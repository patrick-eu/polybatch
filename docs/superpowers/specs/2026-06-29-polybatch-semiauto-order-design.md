# PolyBatch 半自动多腿下单 — 设计文档

日期：2026-06-29
状态：已与用户确认范围，待评审
关联：[2026-06-29-polybatch-design.md](2026-06-29-polybatch-design.md) 的 `submitLeg` 接口完善

## 1. 目标

把已有的下单接口 `submitLeg`（当前为占位的 DOM 填表单框架）完善为可用的**半自动多腿下单**：用户勾选多个 bin、设方向和数量后，插件自动逐个 bin 跑「点 bin → 选方向 → 填数量 → 点 place buy order」序列，用户**只需在 MetaMask 点签名确认**，插件检测到成交后自动进入下一笔。

不在本期：私钥真一键（绕过 UI 直连 CLOB API）——作为后续高级升级，本期预留方向。

## 2. 真实 UI 约束（决定方案的事实）

来自用户实测：
- Polymarket 天气 event 页右侧有**一个固定的下单组件（单例）**。
- 选中某个 bin + 方向后，该组件才变成那个选项的下单（显示价格、数量输入、`place buy order` 按钮）。
- 填数量 → 点 `place buy order` → 弹 MetaMask 签名（Magic 钱包则直接提交）。
- 用户用 **MetaMask**，每笔都弹签名窗，插件无法操作 MetaMask 弹窗。

推论：多腿下单本质是**逐笔**的（单例组件一次绑定一个 bin）；插件不能同时摆多个 bin 的下单，必须一个完成后再下一个，否则切 bin 会冲掉右侧组件里未签完的那笔。

## 3. 方案：半自动序列 + 检测成交衔接

用户要的体验：插件全自动跑序列，用户**唯一动作是点 MetaMask 签名确认**，签完插件自动进下一笔。

**订单类型：限价单挂卖一价（best ask）。** 用户实测下单区是限价模式（有 Limit price 输入）。限价挂在当前最低卖价：立即吃掉卖一档成交、不滑到更深更贵的档；卖一档量够则全部在卖一价成交（零滑点），不够则剩余挂在卖一价等。比市价（深度不足时一路吃更深档）更可控，符合用户「及时成交 + 减滑点」。实现上也免去切 Market（切了限价框会消失）。卖一价由插件从 CLOB 订单簿自动取（asks 最低价），换算成美分填入（Limit price 单位是 ¢，`0.999`→`99.9`）。面板成本显示口径不变（仍按 `calcLegCost` 吃多档均价，作保守上界）。

`submitBatch()` 编排，对每个勾选 bin 依次执行 `submitLeg(leg)`：
1. 点该 bin 行内的 `Buy Yes`（绿）/ `Buy No`（红）按钮 → 右侧组件加载该 bin + 方向（二合一；不点整行 `<a>`，会导航走；方向靠按钮颜色，文本不可靠）
2. 取卖一价、换算美分，填入 Limit price
3. 填入份额（绕过 React 受控组件，原生 setter + input 事件）
4. 点 `place buy order` → 弹 MetaMask
5. 面板显示「第 i/N 笔 · 请在 MetaMask 签名」
6. **轮询检测成交信号**（份额输入被清空 = 该笔已提交）→ 确认该笔完成
7. 自动进入下一个 bin

全部完成 → 面板显示「N 笔已提交」。

## 4. 流程与安全

### 4.1 确认步（保留，真实花钱操作必须）
点面板「下单」后，不立即执行。先在面板内显示确认：
- 「将下 N 笔 · 方向 YES · 共 $X」
- 各 bin 标题 + 数量
用户点「确认下单」才开始 `submitBatch`。防止误触发真实下单。

### 4.2 进度与中止
- 面板显示当前进度「第 i/N 笔 · <状态>」，状态含：切换中 / 等待签名 / 已成交。
- 全程提供「中止」按钮，点击立即停止循环（不影响已提交的笔）。

### 4.3 检测成交的稳健性
- 第 4 步点 `place buy order` 后进入轮询，最长等待 `ORDER_TIMEOUT`（默认 60s）。
- 检测到成交信号 → 进下一笔。
- 超时未检测到 → **暂停**，提示「第 i 笔未确认成交」，给三个选择：继续等待 / 跳过这笔 / 中止全部。绝不盲目连发下一笔。

## 5. 组件与文件

在现有 `content.js`（IIFE）内扩展，不新增文件：
- `submitBatch(legs)`：编排循环 + 确认步 + 进度 UI + 中止。
- `submitLeg(leg)`：单笔序列（点 bin → 方向 → 数量 → place buy order）。替换现有占位实现。
- `waitForFill(timeoutMs)`：轮询检测成交信号，返回 `'filled' | 'timeout'`。
- `PB_SELECTORS`：集中真实页面选择器（见 §6）。
- 确认步与进度复用现有面板 `#pb-total` 区域或新增一个覆盖层。

纯逻辑（可测，抽到 `clob.js` 或单独纯函数）：
- `orderProgressLabel(i, n, state)` → 进度文案（i/n + 状态）。
- 超时判断、循环推进的状态机逻辑做成纯函数，便于 node 测试。

## 6. 选择器依赖（实现第一步从真实页面提取）

`PB_SELECTORS` 需要 6 个真实值，由用户在真实天气 event 页用 DevTools 提供下单区 HTML，由实现者分析得出（不靠猜）：
1. `binItem` — 按 bin 标题定位的可点击温度选项元素
2. `dirYes` / `dirNo` — 右侧组件的 YES / NO 方向控件
3. `amountInput` — 右侧组件的数量输入框
4. `placeOrderBtn` — `place buy order` 按钮
5. `fillSignal` — 成交成功信号（成功 toast 选择器，或「下单组件数量被清空」这一可观测状态）

集中在一处常量，便于页面改版时单点维护、降级。

## 7. 错误处理

- bin 定位失败（`binItem` 找不到）→ 暂停，提示「未定位到 bin『X』，请手动下单后点继续/跳过」。
- 方向/数量/按钮控件找不到 → 暂停提示，不静默跳过。
- 成交检测超时 → §4.3 三选择。
- 计算器（成本显示）与下单解耦：下单序列任何失败都不影响成本计算继续可用。

## 8. 测试

- 纯函数：`orderProgressLabel`、状态机推进、超时判断 → node `assert` 自检。
- DOM 序列（submitLeg/waitForFill）：依赖真实页面，实现后由用户在真实 event 页手动验证（小额真实下单或仅验证到弹 MetaMask 前一步）。

## 9. 实现第一步必须做的

1. 用户提供真实天气 event 页下单区 HTML（右侧下单组件 + 一个温度 bin 元素 + 成交成功 toast），实现者据此填 §6 的 6 个选择器。
2. 先在不真正签名的前提下验证「点 bin → 方向 → 数量 → 停在 place buy order 前」整条 DOM 序列正确，再接通点击 place buy order 与检测成交。

## 10. 后续升级（不在本期）

私钥真一键：插件持专用钱包私钥，对每个勾选 bin 直接构造 CLOB EIP712 订单、本地签名、并发 POST，完全绕过右侧 UI，真正同时成交、彻底消除漂移。需处理私钥本地加密存储与安全边界。`submitBatch` 的上层（勾选/确认/进度）可复用，只替换底层 `submitLeg` 实现。
