# PolyBatch — 设计文档

日期：2026-06-29
状态：已与用户确认范围，待评审

## 1. 问题与目标

用户在 Polymarket 天气市场执行**多腿策略**：同时买入同一 event 下多个温度 bin 的同一方向（YES 或 NO）。当前必须在网页上逐个 bin 分多次手动下单，期间价格和订单簿深度已经变动，导致实际成本偏离预期。

PolyBatch 是一个 Chrome 扩展，目标：
1. **基础**：在一个面板里勾选多个 bin，统一设定方向和每腿 share 数，一次性加速下单。
2. **延展**：实时根据 share 数从订单簿计算每腿成本、总成本与均价。

商业路径：前期免费，后期考虑订阅制。MVP 不含任何付费/订阅逻辑（YAGNI）。

## 2. 关键约束（决定架构的事实）

- Polymarket 用 CLOB（中央限价订单簿）。**每一笔订单必须带钱包私钥的 EIP712 签名**，CLOB API Key 仅用于 HTTP 认证，不能代替订单签名。
- 用户使用 **MetaMask 浏览器钱包**：每笔下单都会弹出 MetaMask 签名窗口。
- 插件**无法操作 MetaMask 的隔离弹窗**（跨扩展 UI）。
- 结论：**"真·一键并发下单、彻底消除漂移" 必须由插件自己持有签名能力（私钥）**，绕开 MetaMask 弹窗。这是物理约束。

## 3. 选定方案：半自动 MVP + 预留私钥升级接口

MVP 不持有私钥、零安全风险。做两件事：
1. **成本计算器**（核心、稳）：纯读公开订单簿，实时算成本。
2. **下单加速**（半自动、尽力而为）：把算好的 share 数预填进页面各勾选 bin 的下单框，用户逐笔点 Buy + MetaMask 签名。

下单动作抽象为统一接口 `submitLeg(leg)`，未来可替换为"本地私钥签名 + 并发 POST CLOB"的真一键实现，不改动上层。

被明确砍掉（YAGNI，验证价值后再加）：popup 弹窗、构建工具/框架、订阅付费系统、私钥签名实现（仅留接口）。

## 4. 交互流程（浮层面板）

在指定市场 event 页面打开插件后，注入浮层：

```
┌─ PolyBatch ──────────────┐
│ 方向:  [ YES ] [ NO ]     │   全局切换
│ 每个 bin 买:  [ 100 ] share│   统一 share 数
│ ─────────────────────────│
│ ☑ 70-72°F   $0.31  $31.0 │   勾选 + 该腿均价/成本
│ ☑ 72-74°F   $0.28  $28.0 │
│ ☐ 74-76°F   $0.15   --   │
│ ☑ 76-78°F   $0.22  $22.0 │
│ ─────────────────────────│
│ 选中 3 腿 · 共 300 share   │
│ 总成本 $81.0 · 均价 $0.27 │   实时
│        [ 下单 ]           │
└──────────────────────────┘
```

操作步骤：
1. 选方向 YES/NO（全局统一）。
2. 输入统一 share 数（每个勾选 bin 买相等数量）。
3. 勾选要买的 bin（多选）。
4. 面板实时显示每腿成本、总成本、均价（吃单深度加权计算）。
5. 点「下单」→ MVP 下依次预填各勾选 bin 的下单框，用户逐笔点 Buy + MetaMask 签名。

注：均价随 share 数变大而变差（吃更深的单），计算会如实反映滑点。

## 5. 组件与文件结构（最小，无构建步骤，加载已解压扩展）

```
manifest.json     MV3 配置（content script 注入到 polymarket.com 市场页）
content.js        注入浮层、读取页面拿 bin 列表、操作 DOM 预填下单框
panel.html / .css 浮层 UI
cost.js           纯计算逻辑：给订单簿 + share 数，吃 ask 深度算总成本/均价/滑点 + 自检 demo
clob.js           调 Polymarket CLOB / gamma API（取 event 的 bin 列表与各 bin 订单簿）
```

各单元职责：
- `cost.js`：纯函数，输入订单簿与 share 数，输出成本/均价/滑点。无副作用、可独立测试。
- `clob.js`：网络层。`getEventBins(slug)` 取该 event 下各 bin 的 `clobTokenId`；`getBook(tokenId)` 取订单簿。
- `content.js`：编排层。注入面板、绑定交互、调用 `clob.js` + `cost.js` 实时更新、实现 `submitLeg(leg)`（半自动版 = 填表单）。
- `panel.html/css`：纯展示。

## 6. 数据流

1. 页面加载 → `content.js` 从 URL 取 event slug → `clob.js.getEventBins(slug)` 拿各 bin `clobTokenId`。
2. 渲染面板，每个 bin 一行带勾选框。
3. 用户改方向/share/勾选 → `content.js` 对每个勾选 bin 调 `clob.js.getBook(tokenId)`（YES 或 NO 侧）→ `cost.js` 算成本 → 更新面板。
4. 点「下单」→ 对每个勾选 bin 依次 `submitLeg(leg)`（半自动 = 定位并预填页面下单框）。

## 7. 错误处理

- 订单簿拉取失败 / 深度不足以吃满 share 数：该腿显示警告（"深度不足"），不计入可下单，总成本标注该腿缺失。
- 拿不到 event bins（页面非天气 event 页 / API 变动）：面板提示"未识别到可批量的 bin"，降级为不渲染。
- 下单加速的 DOM 选择器失效：明确提示"页面结构变动，下单加速不可用"，**计算器仍可用**（能力解耦，单点失效不拖垮全局）。

## 8. 测试 / 自检

- `cost.js` 留一个 `assert` 自检 `demo()`：构造一个已知订单簿 + share 数，验算总成本、均价、滑点是否正确（含"吃穿多档"和"深度不足"两种情形）。
- 不引入测试框架（YAGNI）。

## 9. 实现第一步必须验证的假设

1. **如何取各 bin 的 `clobTokenId`**：候选——`gamma-api.polymarket.com/events?slug=...` 返回的 markets，或页面已注入的数据。实现前先在真实 event 上验证返回结构。
2. **页面下单输入框的 DOM 选择器**：能力②依赖。先在真实页面确认选择器与下单区结构（单 market 视图还是多 bin 同页）。
3. **CLOB `/book` 的字段与 YES/NO token 对应关系**：确认 ask 侧吃单方向、价格单位（0–1 美元）。

这三点若与预期不符，仅影响 `clob.js` 与 `content.js` 的实现细节，不动整体架构。

## 10. 未来升级（不在 MVP）
